# Ostinascope — prototype

> 見えないリズムを、見えている形の中から掘り出す。

スマホのカメラ映像から**繰り返しパターン**（縞・格子・点の並び・同心円／放射、似たものの並び）を検出し、種類に応じたループを鳴らす Web アプリのプロトタイプ。
スマホを動かすことがそのままミックスになる。企画書：`サウンドビジュアル_企画書.md`（Obsidian）。

ビルド不要の静的サイト（ES Modules）。依存パッケージなし。

---

## 動かす

| 目的 | コマンド | 開く URL |
| --- | --- | --- |
| PC で試す（デモポスター） | `python3 scripts/serve.py` | http://localhost:8000/?mode=demo |
| PC のカメラで試す | 同上 | http://localhost:8000/ |
| スマホ実機で試す（同じ Wi-Fi） | `python3 scripts/serve.py --https` | 表示される `https://<LAN-IP>:8443/` |
| テスト | `npm test`（= `node --test test/*.test.mjs`） | — |
| ポスターの紙面を編集 | `python3 tools/poster-editor/serve.py` | http://localhost:8010/tools/poster-editor/ （使い方は `tools/poster-editor/README.md`） |

- カメラは **HTTPS か localhost** でしか使えない。`--https` は自己署名証明書を `.cert/` に作る（git 管理外）。iPhone では警告画面で「詳細を表示 → このWebサイトを閲覧」。
- 安定した実機テスト・展示は **GitHub Pages**（https://trow16.github.io/ostinascope/）で。`main` にプッシュすると `.github/workflows/pages.yml` が自動で公開する：
  1. テスト（`npm test`。処理速度のテストだけは GitHub のマシンでは測らない）。落ちたら公開しない
  2. アプリに要るものだけ（`index.html`・`sw.js`・`src/`・`poster/`）を集め、コミットと時刻を `src/build.js` と `version.json` に書き込んで公開。開発用の `bench/`・`test/`・`tools/` は公開しない
  - 進み具合はリポジトリの Actions タブ（Pages）。手動でも公開し直せる（Run workflow）
  - リポジトリの Settings → Pages の Source は「GitHub Actions」のままにしておく
  - 開始画面・設定パネルに `版：d3c8457（11/21 10:02 公開）` と出る（手元で動かしたときは「開発版」）。動いている版より新しい版が公開されていれば、更新ボタンが「新しい版があります — 更新」に変わる
- **更新したのに古い版が動く問題**：GitHub Pages はファイルを 10 分間キャッシュさせるので、スマホでは新旧のファイルが混ざったり、再読み込みしても古いままだったりする（スーパーロードもできない）。`sw.js`（Service Worker）がこれを防ぐ：
  - このサイトのファイルは毎回サーバに確かめてから使う（変わっていなければ「変更なし」の短い返事だけなので速い）。ブラウザ側のキャッシュが古いファイルを使い回さないようにもしている
  - 最後に取れたものを取っておき、ネットにつながらないときはそれで開く（会場の回線が悪くても起動できる）
  - 開始画面と設定パネルに **版（サーバの更新時刻）** と **「最新版に更新」** ボタン。ボタンは全ファイルを取り直して読み込み直す（オフラインのときは何もしない）
  - Service Worker 自体は、入れた直後の 1 回目の訪問ではまだ効かない。1 回目の訪問で入り、開始前ならその場で 1 回だけ自動で読み込み直す。以降はいつも最新
- iPhone は「タップして開始」で音が有効になる。消音スイッチ ON でも鳴るよう `navigator.audioSession` を設定済み（iOS 16.4+）。
- URL に `?debug` を付けると解析セルと統計を表示し、コンソールから `window.ostinascope` で内部状態を触れる。
- 枠をカメラの動きに合わせて動かす「追従」は既定でオン。設定パネルのチェック、または URL の `?nofollow` で切れる（比べるとき用）。

### デモモード
カメラなしで、生成したポスター（パターン標本）を「カメラで覗いている」状態をシミュレートする。
ドラッグで移動、ホイール／ピンチで拡大縮小、6 秒放置で自動巡回。設定パネルから任意の画像を読み込んだり、デモポスターを印刷用 PNG（3600×5092）で保存して実機テストに使える。

## 仕組み

```
カメラ / デモ画像
   │ 2倍ずつ縮小（エイリアシング＝偽モアレ防止）
   ▼
解析画像 192px（短辺）── 10 Hz ── Web Worker ──┐
   │                                            ▼
   └─ 約 30 Hz ── motion.js  カメラの動き（角の追跡＋平面の射影変換）
 detector.js  半分ずつ重ねたセル(32×32)ごとに 2D FFT ×4 階層（1×・2×・2.8×・4× 縮小）
   │  縞 / 格子 / 点 を判定 → 隣接セルを統合 → 同心円・放射は向きの収束で判定
   │  plane.js  縞・格子の歪み方から、模様の載った面の傾きを求める
   ▼
 tracker.js   フレーム間で ID を追跡（数フレームで確定、見失ったらフェード）。
              解析の合間はカメラの動きで枠を面ごと動かす
   ▼
 mapping.js   パターンの性質 → ループ（拍の分割・音高・音色・音量・定位）
   ▼
 audio.js     共有テンポ上で先読みスケジューリング（Web Audio, 全音源シンセ）
 render.js    検出領域・寸法線・注記・出口の痕跡・スコアを重ねて描画
```

### 検出（`src/detector.js`）
1. 画面を 32×32 px のセルに分ける。セルは**半分ずつ重ねて**並べる（模様がセルの格子とずれていても、どこかのセルにきちんと収まる）。
2. 解像度を変えた **4 階層**（192px 短辺の 1×・2×・2.8×・4× 縮小）で同じことをする。細かい模様は 1×、大きな模様は粗い階層が担当し、画面幅の約 1.4%〜29% の間隔を拾う。近づく／離れると担当が切り替わる。
3. セルごとに平均を引いて Hann 窓 → 2D FFT（実数入力用に半分の計算量）→ パワースペクトルの極大を探す。
4. 「繰り返し」と認める関門（どれかに落ちたら鳴らさない）：
   - **突出度**：同じ半径の帯の中央値の 20 倍以上（ランダムな質感は数倍止まり）
   - **鋭さ**：ピーク周り 5×5 のエネルギーのうち 85% 以上が中心 3×3 にある（髪・葉・砂利などの質感は山が広い）。突出度が 100 倍を超える強いピークは 70% で可（波打つ金網、斜めから見た紙）
   - **3 回以上の繰り返し**：周期方向の 1 次元プロファイルが 2 周期先と相関 0.35 以上（遠近で間隔がずれるので ±15% の幅で探す。平行線 2 本・紙の縁＋枠線などを除外）
   - **集中度**：模様の周波数より上の帯域で、1 方向（＋倍音）がエネルギーの 20% 以上（格子は 2 方向で 30%）。陰影や大きな輪郭の低周波は数えない
5. 2 方向目のピークがあれば格子。交差項（k1±k2）が強ければ **DOTS**、弱ければ **GRID**。
6. 同じ種類・周期・向きの隣接セルを統合（階層ごとに最低 3/2/2/1 セル。それより小さい領域は突出度 1000 倍以上などよほど明瞭な場合だけ）。小さな隙間は橋渡し、関門をわずかに外したセルは領域の縁として取り込む。格子の縁で片方向しか見えないセルは格子に吸収。
7. 縞セルの集まりで向きが扇状に広がっていれば、各セルの法線（同心円）／縞の向き（放射）が 1 点に収束するかを最小二乗で確認する（リングは斜めから見た楕円として）。ずれは角度で測り、中心を向かないセルは除いて当てはめ直す → **CONCENTRIC / RADIAL**。
8. 同心円・放射は画素ごとの輪郭の向きからも探す（`src/centers.js`）。不揃いな年輪、細くなっていく花びら、中心が画面の外の輪はセルに縞を作らないので、7. では拾えない。
   - 半分の解像度で各画素の輪郭の向きとそのはっきりさを求め、はっきりした画素がその近く（40px）にだけ中心の候補を投票する（輪なら勾配の向きに、放射なら輪郭に沿って）。散らかった画面でも、1 つの切り株・1 つの花の中心が局所の山になる。画面の外にも余白をとって投票する。
   - 候補ごとに、まわりの画素の向きが輪（勾配が中心を向く）／放射（勾配が中心と直角）にどれだけそろうかと、そろう扇形（16 分割）がどれだけ広い弧に続くかを見る。まっすぐな縞は向かい合う 2 つの細い扇、格子は 4 つの扇でしかそろわない。
   - 輪は中心から外へ明暗が 6 回以上入れ替わること（ぼけた丸 1 つの縁は 1 回）。
   - 同じ場所に 7. の同心円・放射があればそちらを残す。
9. 色は領域内の「より彩度の高い側」（色インク or 色紙）から取る。

解析は Web Worker で行う（スマホで 1 フレーム 10〜40 ms 程度でも描画と音のスケジューリングが止まらない）。間に合わないフレームは捨てる。

### 似たものの並び（`src/rows.js`）
縞の FFT は「同じ模様が等間隔」でないと拾えない。棚の瓶、並んだ椅子、建物の窓のような**似たものの並び**は、自己類似で別に探す。
1. 縮小画像を 4×4 px のブロックに分け、ブロックごとに輪郭の向きのヒストグラム（6 方向）を作る。
2. 3〜6 ブロックの窓ごとに特徴（3×3 区画 × 向き＋明暗の配置、63 個の数）を作り、似ているかをコサイン類似度で比べる。
3. 輪郭の多い窓を「基準」にして画面全体を探し、画面の典型的な似かたより飛び抜けて似ている窓を「そっくりさん」とする。
4. そっくりさんが基準と合わせて **3 つ以上ほぼ一直線に並んでいれば ROW**。間隔は不揃いでもよい（ばらつき 55% まで。3 つだけの時は 30% まで）。
5. 誤反応を避ける条件：
   - 隣り合う 2 つの間に「似ていない所」がある（1 本の長い線や輪郭は端から端まで似ているので並びではない）。
   - そっくりさんの半分以上が並びの線上にある（画面中どこにでもいるなら質感）。
   - 画面の 1/4 以上と似ている基準は使わない（質感・格子）。
   - すでに縞・格子と分かった領域の中では探さない。同じ間隔の縞・格子と重なる並びは捨てる（同じ繰り返しを二重に鳴らさない）。

6. そっくりさんが 2 方向に並んでいれば**似た物の格子**（GRID）。レンガ・タイル・キーボード・ビルの窓・蜂の巣のように、1 つずつ色や汚れが違って FFT ではきれいな山にならないものを拾う。
   - そっくりさんどうしの近い方へのずれから、格子の 2 本のベクトルを求める。
   - 基準から格子を 1 歩ずつたどり、着いた所のまわりで次の物を探す。斜めから見て歪んだ格子にもついていける。
   - 4 つの物が 1 歩ずつ離れて囲む「まるごとのマス」が 2 つ以上必要で、その角の物だけを数える（偶然似ていた点や、1 列の物の上と下を「2 列目」と読む誤りを捨てる）。
   - 隣どうしの中間で、2 方向とも似ていない所があること（縞は線に沿って同じ見た目が続くので、これがないと縞の板を格子と読む）。
   - 格子の範囲の中で、画面全体から集めたそっくりさんが格子の物であること（なめらかな雑音や板目では、1 歩先には必ず似た窓があるが、いちばん似た窓は格子の間に散らばる）。
   - FFT の格子と同じ場所なら FFT の方を残す。縞の領域の小さな一部に縞に沿って出た格子は、縞が背後の物と交差しただけとして捨てる（柵ごしの屋根）。並びの物が格子の物なら、その並びは格子の一部。

細かい階層・粗い階層の 3 段で探す（画面幅のおよそ 6%〜40% の大きさの物）。重いので、アプリでは 3 段を 2 フレームに分けて交互に探す（`rowSplit`）。

### 面の傾き（`src/plane.js`）
- 平面に印刷された模様を斜めから見ると、奥ほど間隔が詰まり、線は消失点へ向かって集まる。模様の位相は φ(x) = p·x / (c·x + 1) の形になり、c·x + 1 = 0 がその面の**消失線**（同じ面のどの模様でも共通）。
- 検出器はセルごとに間隔と向き（＝局所的な周波数 ∇φ）を測っているので、縞・格子の領域ごとにこの式を当てはめる（Levenberg–Marquardt）。格子は 2 方向で消失線を共有させる。傾きのない式（周波数が一定）より明らかによく説明できるとき（F 検定）だけ傾きを認める。9° 未満は正面とみなす。
- 消失線とカメラの焦点距離から面の向き（法線）が決まり、面を正面から見た形に直せる。これを使って
  - 枠を面に沿った形（斜めの面では台形）にする。注記に `傾き 30°` のように出る
  - 格子・点の間隔比を正面から測る。斜めから見た 3 : 4 の格子は 3 : 3.3 や 3 : 6 に見えてしまうが、印刷どおりの 3 : 4 のポリリズムで鳴る
- 焦点距離は機種やズームで違うので、**傾いた格子から学習する**。格子の 2 方向は紙の上では直角に交わるので、消失線が分かれば焦点距離が 1 つに決まる。最近の推定の中央値を使い、5 回分たまるまでは既定値（画面短辺の 1.6 倍 ≈ 34°）を使う。
- 外れた当てはめ（画面の縁で切れた領域など）で枠が細長くなる・極端に大きくなるときは、傾きを採用しない。

### カメラの動きへの追従（`src/motion.js`）
- 解析（10 Hz）の合間も、枠が見つけた面に貼り付いて動くようにする。カメラの新しいフレームごと（約 30 Hz）に次の 3 段で動きを求める。
  1. 角を拾う（Shi–Tomasi。画面に散らばるよう、16px のマスに 1 つまで）
  2. 各角を次のフレームへ追う（ピラミッド Lucas–Kanade、3 階層・7×7 の窓）。逆向きにも追って元に戻らない角は捨てる
  3. 追えた角に RANSAC で射影変換（ホモグラフィ）を当てはめる。これが画面でいちばん大きな平面の動き。スマホを回すだけなら奥行きに関係なく正確で、平らなポスターなら平行移動しても正確
- 各トラックは四隅（四角形）を持ち、毎フレームこの変換で動く。斜めに見ている面では、動くにつれて台形に歪む。
- 解析結果は Worker から 1〜2 フレーム遅れて戻るので、撮った時点から今までの動きを掛け合わせて、今の位置に移してから追跡に渡す。
- 枠は面に貼り付いているので、新しい検出を取り込むときは強めに平滑化しても遅れない（`smoothPosMoved` 0.25。追従なしは 0.5）。検出の枠は解析セル単位でがたつくため、そのがたつきを抑えられる。
- 動きが求められないとき（無地の壁・強いぶれ・画面の急な切り替え）は、そのフレームは動かさず従来どおりに戻る。
- 1 フレーム約 3 ms（PC の Chrome。メインスレッド）。重ければ Worker に移せるよう DOM 非依存にしてある。

### 面を動きで分ける（`src/motion.js`・`src/follow.js`）
- スマホを回すだけなら、奥行きに関係なく画面全体が 1 つの射影変換で動く。歩く・横にずらすなど平行移動すると、近い床と遠い壁で動き方が変わる（視差）。この違いで面を分ける。
- 1 フレーム（1/30 秒）では床と壁の差は 1px 前後しかないので、角ごとに直近 8 フレームの位置を覚えておき、**7 フレーム（0.23 秒）ぶんの動き**で分ける：いちばん大きな面の射影変換、それに合わない角でもう 1 つ…と最大 3 面まで。新しい面は、角が 10 個以上・全体の 6% 以上あり、最初の面の動きから 2px 以上（すでに追っている面なら 1.2px 以上）外れているときだけ認める。
- 面ごとに、そのフレームの動きを自分の角だけで当てはめ直す。面の ID は角を通じて引き継ぐ。
- 新しい角は、角の少ない場所から優先して拾う（コントラストの強いポスターのそばの、淡い床にも角が付くように）。どの面にも合わない状態が 3 フレーム続いた角は捨てる。
- 各トラックは、枠の中の角が属する面（6 割以上が同じ面）の動きで動く。分からなければ前の面、それもなければいちばん大きな面の動き。解析結果を今の位置に移すときも同じ。
- 面が 2 つ以上見つかったときは、それぞれの角の範囲を薄い点線で囲んで `面A ∠32°` のように表示する（傾きは、その面の上の模様から求めたもの）。枠の注記にも `／ 面B` と付く。

### 奥へ続く並び（`src/rows.js` の 5.）
- 奥へ続く並び（椅子・柱・柵・棚を斜めから）は、遠くの物ほど小さく、間隔も詰まって写る。そのままでは等間隔の並びが加速するリズムに聞こえ、遠くの物は小さすぎて見つからない。
- 並びの物それぞれの見かけの大きさを測る（基準の物と最も似る窓の大きさ。窓は小数ブロックの大きさ・位置で取れるようにした）。同じ大きさの物がまっすぐ並んでいれば、見かけの大きさは並びに沿って直線的に縮み、消失点で 0 になる：w = a (t − t_v)。実際の位置は X = −1/(t − t_v)（定数倍とずれを除いて）。大きさに 1 本の直線を当てはめて消失点を求め、**実際の間隔でリズムを鳴らす**。
- 同じ式で次の物の位置と大きさが予測できるので、その大きさの窓で探して並びを両端へ伸ばす（遠くの小さな物まで拾える）。
- 奥へ続くとみなすのは、像の間隔が一方向に変化し、大きさが同じ向きに 1.3 倍以上・並びの順に揃って変わり、直線によく乗るときだけ。正面から見た並びは今までどおり。注記に `遠近×1.9`（端から端の大きさの比）と出る。
- 実物は大きさがそろわないので、大きさの直線が決まらないことが多い。実物の並び（椅子・柱・窓）はたいてい等間隔なので、そのときは**間隔から**読む：等間隔の並びの像は i 番目の物が t = (α i + β)/(γ i + 1) の位置に来る（見つからなかった物は、間隔が約 2 倍に空くので 1 つ飛ばす）。ただし、わざと不揃いに並べた正面の棚（9 : 9 : 12 : 15 など）もこの式にほぼ乗ってしまうので、大きさで確かめる：遠近なら間隔は距離の 2 乗、大きさは距離に比例して縮むので、大きさの変化が「間隔から見込まれる量の平方根」と合うときだけ採用する（正面の棚は大きさが変わらないので採用されない）。

### 追跡（`src/tracker.js`）
- 3 フレーム（≥250 ms）連続で見えたら確定 → ループ開始。
- 350 ms 見失ったらフェードアウト開始（縞 1 小節、その他 2 小節）。途中で戻れば復帰。
- 画面の縁から出て行った場合は、出た方向の縁に痕跡（矢印と注記）を残す。

### 音（`src/mapping.js`, `src/audio.js`）
| パターン | ループ |
| --- | --- |
| STRIPE | 間隔で拍の分割：細 → 1/16・1/8（ハイハット）、粗 → 1/4・1/2（キック） |
| GRID | 2 つの間隔の比を小さな整数比に丸めてポリリズム（例 3:4 → 3 対 4） |
| DOTS | ユークリッド・リズム E(k,16)（密なほど k が大きい）の短い打音、音程は輪郭パターン |
| CONCENTRIC / RADIAL | ドローン（根音＋5度＋オクターブ）。テンポ同期のフィルタのうねり |
| ROW | 並んだ物 1 つにつき 1 打の木質の打音。**並びの中の位置がそのまま小節内の位置**（等間隔なら均等、不揃いなら不揃いのリズム）。並びの線より上にある物は高い音、下は低い音。大きな物ほど低く長い |

| 見た目 | 音 |
| --- | --- |
| 色 | 音高（D マイナー・ペンタトニック。黄＝高い、青＝低い、無彩色＝根音） |
| シャープネス（倍音の強さ） | アタック・硬さ |
| コントラスト・面積 | 音量 |
| 縞の向き | パン（45° と 135° が左右に分かれる） |

- テンポは全体で 1 つ（既定 108 BPM）。新しいループは**次の拍の頭**から入り、構造の変化（分割・比など）は 3 回連続で要求されたら**次の小節線**で切り替わる。
- まったく同じループになるパターン（同じ図形が並んでいる等）は 1 声にまとめて鳴らす（注記に `＝05` のように表示）。
- 同時に鳴るループの上限（既定 6）を超えた分は `MUTED` 表示。

## 現状と次にやること

確認済み（PC の Chrome）：デモポスターで全種類が検出され、Worker 上で 1 フレームあたり約 15 ms・10 Hz で解析できる。印刷したポスターを手持ちで撮った映像（傾き・ぼけ・手ぶれ・照明むら・ノイズを付けたもの）を Chrome の疑似カメラに流すと、各図の前で正しい種類のループが鳴っている割合は 100%（32/32 サンプル）。

カメラで反応が鈍かった点の見直し（2026-11）：実写写真 82 枚（Wikimedia Commons：ブラインド・横断歩道・階段・鍵盤・レンガ・金網・キーボード・水玉・建物の窓など＋人物・自然・食べ物・机）から切り出した 1,640 ビューと、実写背景に模様を合成した 300 枚・手持ちの連続フレーム 60 本で旧版と比べた。
- 4 周期以上見えている模様の検出率：細かい模様 73% → 93%、粗い模様 40% → 70%
- 実写写真で反応したビュー：横断歩道 35% → 61%、階段 36% → 64%、鍵盤 19% → 41%、フェンス 18% → 43%、金網 11% → 26%、キーボード 33% → 51%
- 手持ちで模様に向けてから鳴るまで：遅い側（90 パーセンタイル）1.5 秒 → 0.4 秒。見えている間に鳴っている割合 54% → 78%
- 模様のない場面（人物・自然・机など）で鳴り始めるループ：毎分 9 → 13.5。増えた分の多くは背景にある本物の繰り返し（チェックのシャツ、本棚、象嵌の縞など）
- 原因は主に 3 つだった：セルが重ならず模様がセルの格子とずれると拾えない／粗い模様（画面幅の 13% 超）を見る階層がない／「全エネルギーの 40% が 1 方向」という条件が、陰影や輪郭の多い実写では満たせない

似たものの並び（2026-11 追加）：
- 実写背景に物を 3〜7 個並べた合成画像で、並びを正しく見つけたのは 44%（見つけたもののうち個数が ±1 以内に合っていたのは 31/38）。手持ちの連続フレームでは、並びに向けた場面の 75% でループが鳴り始める
- 模様のない場面（人物写真）で誤って鳴り始める ROW は 40 秒に 1 回程度
- 実写写真（40 ビューずつ）で ROW が出たビュー：瓶 6・椅子 8・カップ 5・瓶詰 14・街灯 5・靴 3。ピアノの黒鍵（16）やキーボード（12）も並びとして拾う
- 苦手：見た目のばらつく物（銘柄の違う瓶、遠近で大きさが変わる椅子。同じ形の物が奥へ続く並びは 2026-11-20 から実際の間隔で読む）、縦長の物 1 つの中の似た部分を縦の並びと誤認することがある
- 解析時間が増えた（PC の Chrome の Worker で 1 フレーム約 30 ms。以前は約 15 ms）。スマホでは 10 Hz を下回る可能性がある
- デモポスターに fig.9（瓶 5 本、間隔 15 : 15 : 20 : 25u）を追加

感度の初期値を 1.0 → 1.3 に（2026-11-20）：
- 感度スライダー（0.6〜2.0）が並びの閾値にも効くようにした。緩めるのは測って効いたものだけ：隣どうしの間で似ている度合いが下がる量（`minDip`）、線上にある似たものの割合（`onLine`）、3 個の並びの類似度（`minSim3`）、間隔のばらつき（`maxUneven`）。類似度の下限そのものを下げると何でも似て見えて逆に悪くなる。3 個の並びでは `minDip` は緩めない（ノイズの模様がここで並びに化ける）
- 格子（2 方向目）には感度を 1.1 までしか効かせない。2 つの縞の境目に偽の格子が出るため
- 合成画像の並び 44% → 55%、手持ちの連続フレームで鳴り始めるのは 69% → 75%。写真で何か反応したビュー：瓶 14 → 20・カップ 10 → 14・柵 17 → 20・レンガ 13 → 17（各 40）
- 代わりに模様のない連続フレームでの誤ったループは 13.5 → 16.5 回／分。うるさければスライダーを 1.0 に戻せばほぼ元の挙動

自然物に反応するよう感度の初期値を 1.3 → 1.8 に（2026-11-20）：
- 自然物の写真（年輪・花・松ぼっくり・鱗・蜂の巣・砂紋など 14 種）で調べると、落ちている理由はほぼ「鋭さ」と「繰り返し」。自然の繰り返しは規則が少し揺らぐので、ピークがにじみ、2 周期先の一致も弱い
- 感度 1 を超えると鋭さの基準（0.85）と繰り返しの基準（0.35）も下げる（感度 2 で 0.6 / 0.25）。その緩めでやっと通るセルだけの領域は、セル 3 個ぶん広くないと認めない（`softCells`。少しのセルだけなら輪郭や服のしわ）
- 並びは感度 1.3 までしか緩めない（`rowSensitivityMax`。それ以上はノイズが並びに化ける）。格子の 2 方向目は 1.1 まで
- 同じ模様を 2 つの階層で見たとき、粗い階層の枠がはみ出しても 1 つにまとめる
- 写真で何か反応したビュー（各 40）：年輪 13 → 23・蜂の巣 27 → 30・花 15 → 18・砂紋 30 → 32・木目 34 → 37。苦手なまま：葉・並木・小石・波（7〜10）
- 模様のない連続フレームでの誤ったループは 16.5 → 24 回／分。スライダーは 0.6〜2.5

同心円・放射の取りこぼしと、カメラが止まったときの鳴りっぱなしを修正（2026-11-20）：
- 同心円にまとめる段階で落ちていた。原因は 4 つ：リングの外の縞のセルまで同じかたまりに入る／中心への当てはめ誤差を px の距離で測っていたので大きいリングほど落ちる／斜めから見たリングは楕円で、法線が 1 点に集まらない／周期を 2 倍に読み違えたセルが少しあるだけで不合格になる
- リングは同心の楕円として当てはめる（中心と楕円の形を未知数にした線形最小二乗。`ringEllipse` 0.5 まで平たいものを許す）。放射は遠近でも直線のまま 1 点に集まるので、そのまま
- 当てはめのずれを角度で測り（`ringAim` 0.07）、中心を向いていないセルを外して当てはめ直す（`ringOutlier`。ただし元の 6 割は残ること＝`ringKeep`）。それでも駄目なら、かたまりに混ざったまっすぐな縞の部分を除いてもう一度試す。周期は大半のセル（`ringSpacing` 7 割）が中央値に近ければよい
- 同心円・放射の領域の上に重なって出る縞の領域は、向きがその中心と合っていれば同じ図の一部として消す
- 同心円・放射の合成シーン：同心円 4 → 11 / 29、放射 10 → 17 / 32。斜めから見たリング（合成）11 → 16 / 16、縞の隣にあるリング 0 → 5 / 5
- 誤検出は減った：実写写真で模様のない所に出た同心円・放射 42 → 19、合成シーンの模様の外 24 → 8。波・蜂の巣・机に出ていた偽の放射が消え、年輪が同心円として出るようになった。代わりに花の放射は 5 → 2（40 ビュー中）
- デモポスターのレコード（fig.4）で同心円と判定される画角 12 → 16 / 20。ほかの種類・誤ったループの数・解析時間は同等
- カメラの映像が止まる（iPhone で裏に回して戻る、他のアプリにカメラを取られる）と、止まった 1 枚を解析し続けてループが鳴りっぱなしだった。止まったら 0.4 秒で音を消し、映像の再生を再開する。カメラが切れていたら開き直す（3 秒おき）

枠をカメラの動きに合わせて追従（2026-11-20）：
- これまでは解析（10 Hz）のたびに枠を置き直していたので、スマホを動かすと枠が面から遅れて飛んでいた。カメラの動き（`src/motion.js`）で、解析の合間も枠を面ごと動かすようにした。Worker から遅れて戻る解析結果も、今の位置に移してから使う
- 評価（`bench/follow.html`）：仮想のスマホカメラ（画面短辺で約 38°）がデモポスターや写真の上を 3 次元的に動く（傾き・パン・寄り引き・手ぶれ。真の動きが分かっている）。枠が下の面に対して 1 フレームにずれる量（192px の画面で）：
  - ポスター（8 本）：平均 2.9 → 1.1px、速く動かしているとき 4.8 → 1.2px、新しい検出を取り込むときの飛び 5.5 → 3.3px
  - 写真（横断歩道・建物・レンガ・階段・部屋・街）：平均 3.4〜4.9 → 1.1〜2.1px、速く動かしているとき 5.6〜7.3 → 1.1〜3.4px
  - 見えている図が鳴っている割合 77 → 78%
- 解析の合間はほぼ面に貼り付いている。残るずれの大半は、新しい検出を取り込むときの飛び（検出の枠が解析セル単位でがたつくため）
- 追従の処理は 1 フレーム約 3 ms（PC の Chrome）。追従なしの挙動・検出の結果は変わらない（連続フレームの評価で同一）
- ついでに見つけた不具合：並びの物が画面の縁で切れていると、その明暗（音量に使う）が NaN になり、音量の設定で例外が出ていた。画面の外を読まないよう修正

模様の歪み方から面の傾きを求める（2026-11-20）：
- 斜めから見た模様は、奥ほど間隔が詰まり線が集まる。その歪み方から面の向きを求め（`src/plane.js`）、枠を面に沿った台形にし、格子の間隔比を正面から測るようにした
- 合成画像（カメラが既知）：面の法線の誤差 0.3° 前後、正面の模様を傾いていると誤ることはなし。斜めから見た 3 : 4 の格子は、見たままでは比の誤差 11〜15%（3 : 3.3 や 3 : 6 に丸まる）→ 正面から測ると 1% 前後
- 焦点距離を間違えると傾きが 10° 前後ずれ、格子の比はかえって悪くなることがあった。傾いた格子から焦点距離を学習するようにして解決（真の値 1.1 / 1.6 / 2.2 に対して 1.10 / 1.62 / 2.22）
- 動くカメラでの評価（ポスター 8 本）：傾きの誤差の中央値 3.5°（悪い側 1 割で 17°）。20° 以上傾いた画面の 79% で傾きを認識、正面の画面で誤って傾きを付けたのは 1%。fig.2（3 : 4 の格子）が 3 : 4 のポリリズムになる割合 64 → 85%。学習した焦点距離 1.52（真の値 1.45）
- 写真の評価は、写真そのものに写っている奥行き（道路・部屋）があるので正解が分からず、傾きの精度は測っていない

音が止まったときに過去のループが画面の下にたまり続けるのを修正（2026-11-21）：
- iPhone では音の文脈（AudioContext）が中断されることがある（電話・ほかのアプリの音・画面収録の開始など）。その間は音の時計が止まるので、見失った模様のループのフェードが終わらず、下の一覧に増え続けていた（届いた画面収録では、小節の表示が 8 秒間 186.3 のまま、一覧は 15 行ほど）。解析は動き続けるので、新しいループも足されていた
- 止まっている間は、フェード中のループをその場で外す（音は出ていないので聞こえ方は変わらない）。1 秒おきに再開を試し、画面のどこかをタップしても再開する。止まっている間は下の帯に「音が止まっています — 画面をタップで再開」
- ヘッドレスの Chrome のデモで、音の文脈を止めて再開もできないようにして確かめた：直す前は 20 秒で一覧 8 → 12（フェード中 5 → 9）、再開を許しても止まったまま。直したあとは一覧 2〜4（フェード中 0）、再開を許すと 3 秒以内に鳴り出す
